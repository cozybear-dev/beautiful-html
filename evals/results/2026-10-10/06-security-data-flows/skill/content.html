Inside our network, customer data is stored only in the data zone, and one connection there is not encrypted

A request leaves the customer’s browser, passes the CDN and web application firewall and then the load balancer at the edge, and reaches the web application or the API service. The API service writes customer records to the primary database and uploaded documents to document storage. Both are in the data zone.

How to read the figure

Each frame is a network zone. Shape shows what a system is: a cylinder stores data, cut corners mark a gateway. The label on each arrow is the encryption on that connection. Use the arrow buttons to follow the data one stage at a time.

Work that does not have to finish within the request, such as sending email and updating the search index, goes through a job queue to background workers. The search index and the reporting warehouse hold pseudonymised data only. Three systems are outside our network: the identity provider used for single sign-on, the email provider and the log platform. Figure 2 shows what is sent to each.

One internal connection is not encrypted, and it is scheduled for replacement

Each night the primary database exports data to the reporting warehouse. That export runs over FTP on port 21, with no encryption in transit, and authenticates with a shared password. It is the only one of the seventeen connections that is not encrypted, and the only one that uses a shared password.

Two things limit the exposure. The export contains pseudonymised data, not the customer records themselves. And both systems are in the data zone, so the connection stays inside the private network. We rate the risk as medium. The connection does not meet the standard of the other sixteen, and we are replacing it.

Known gap

The nightly export from the primary database to the reporting warehouse uses unencrypted FTP with a shared password

Risk: medium. Remediation: replace the export with TLS-encrypted managed replication. Due: 30 November 2026. Owner: Analytics team.

Each of the other sixteen connections is encrypted with TLS and authenticated

The table lists all seventeen connections in the order data travels. Seven use TLS 1.3 on port 443: the two edge connections, single sign-on, document storage, email and both log connections. The other nine, into and within the application and data zones, use TLS 1.2.

Authentication

Connections from the CDN to the load balancer and from the load balancer into the application zone use mutual TLS. Access to the primary database and document storage is by IAM role. The search index, the email provider and the log platform are called with API keys.

Four connections leave our network, and one of them carries personal data to a subprocessor

Background workers send the recipient’s email address and the message body to the email provider, Sendwell Inc., which delivers transactional email. The API service and the workers send application logs to the log platform, Logline Ltd.; the logs are scrubbed and contain no personal data. Both subprocessors process in the EU.

The fourth connection is sign-in. The web application exchanges SAML or OIDC messages with the identity provider, which is either the customer’s own or Okta. Credentials are held by the identity provider; none of our systems is recorded as storing them.

Stored customer data is encrypted with AES-256 and kept in the EU

Four systems of ours store customer data: the primary database, document storage, the search index and the reporting warehouse. All four are encrypted at rest with AES-256. Keys are held in a managed key management service and rotated yearly.

All production systems run in the EU, in Frankfurt and Dublin. The edge systems and the web application store no customer data; the API service, the background workers and the job queue handle personal data only while it is in transit.

What the encryption-at-rest column covers
