Growth team Experiment readout: CHK-212, single-page checkout

The single-page checkout wins on desktop but not on mobile web: ship it to desktop and tablet, hold mobile

Over four weeks the new checkout turned 3.38% of visitors into orders, against 3.18% for the current one. That is 6.3% more orders per visitor, and a gap this large is very unlikely to be chance. All of the gain came from desktop and tablet. On mobile web, where the pay button can fall below the fold, the new checkout did no better and probably slightly worse.

The new checkout took more orders on every one of the 28 days

Half of visitors saw the new single-page checkout and half saw the current three-step one. From almost identical traffic, the new checkout took 9,596 orders against 9,029: 567 more orders and about €31,400 more revenue in four weeks.

How the test ran

Visitors were split 50/50 at random: 284,037 saw the new checkout and 284,134 the current one. The split is as even as it should be, and the test ran its full planned four weeks.

We can be confident it is better, but expect about 5%, not 6%

Three things say the win is real. If the two checkouts were truly equal, a gap this size would turn up by chance fewer than 1 time in 10,000. The new checkout was ahead on all 28 days, not just on average. And the likely range for the true effect, +3.4% to +9.4%, sits entirely above the +3% the test was designed to detect.

What "likely range" means

No test gives one exact answer. The likely range is where the true effect sits with 95% confidence: ranges built this way contain the truth 19 times in 20. A range that includes zero means we cannot tell a gain from a loss.

One caution on size. The lift was 11.6% on day one, fell each day of the first week, then held between 4.4% and 6.3%. That is the usual pattern when something new gets extra attention at first. Counting weeks two to four only, the lift is +5.3% (likely range +1.9% to +8.8%). Plan on about 5%, and note that we cannot rule out a settled effect a little under the 3% target.

No guardrail was broken

Revenue rose with orders. Baskets were slightly smaller, so revenue per visitor grew a little less than orders did.

The gain is all on desktop and tablet; mobile web did not improve

The answer is not the same for everyone, and device is what separates them. On desktop the new checkout lifted orders per visitor by 11.1%. On mobile web, which is about half of all visitors, it was 2.3% lower. Desktop and tablet together produced 757 more orders than the current checkout; mobile web produced 123 fewer.

How sure is this? Mobile's range runs from −5.8% to +1.4%, so we cannot say for certain that the new checkout is worse there. We can say it is not delivering the desktop gain: the gap between desktop and mobile is far too large to be chance (fewer than 1 in 100,000). Tablet points the same way as desktop, but tablets are 8% of visitors and its range is too wide to be sure alone.

The likely cause is already known. On mobile web the single page pushes the pay button below the fold on screens under 700 px tall. We have no split by screen height, so this data cannot prove that is the reason, but it is the obvious suspect and it is fixable.

New and returning customers responded alike. Within each device the two groups move in the same direction by a similar amount, so customer type does not change the decision.

One thing to settle: the device file does not add up to the headline file

The device breakdown counts about 431,000 visitors and 12,800 to 13,400 orders per checkout. The daily file behind the headline counts about 284,000 visitors and 9,000 to 9,600 orders. The two exports are evidently counting differently, and we do not yet know why. Both are evenly split between the checkouts and both show the new one ahead overall (+4.9% in the device file, +6.3% in the daily file), so the device pattern stands. The exact device figures should be confirmed with the data team before they are used to size the rollout.

Recommendation: ship to desktop and tablet now, fix mobile web and test it again

Recommendation

Ship the single-page checkout on desktop and tablet. Keep mobile web on the current checkout until the pay button is fixed and re-tested.

Desktop is a clear win at +11.1% (likely range +7.4% to +14.9%) with no guardrail broken. Mobile web is half of our visitors and showed no gain, so shipping there now adds risk and no benefit.

Ship everywhere

Captures the desktop gain, but puts half of visitors on a checkout that was 2.3% behind for them, with a known layout fault.

Recommended: desktop and tablet only

Captures all of the measured gain. Mobile web stays as it is today, so nothing is lost while the fix is built.

Do not ship

Gives up a desktop gain we are confident in. Nothing in the results supports this.

What happens next

  1. Now

    Roll out to desktop and tablet

    Tablet is a judgement call: it was ahead but too small to be sure, and the pay button fault is specific to short mobile screens.

  2. Before sizing

    Reconcile the device file with the daily file

    So the rollout forecast rests on confirmed device figures.

  3. Next

    Fix the pay button on mobile web, then run a mobile-only test

    Four weeks of mobile traffic pins the effect down to within about ±3.6%.

  4. After launch

    Watch conversion and payment errors for four weeks

    Forecast on a settled lift of about 5% overall, not the 6.3% headline. The desktop figure probably includes some first-week boost too.

Method

Headline figures use daily.csv: 284,134 visitors and 9,029 orders on the current checkout, 284,037 visitors and 9,596 orders on the new one. Changes are relative differences in orders per visitor. Likely ranges are 95% confidence intervals for that relative difference, and the chance figures come from a two-sided test of two proportions, at the 5% significance level set in the design. Device and customer-type figures use segments.csv. Six segments were examined; the desktop result and the desktop–mobile gap remain far beyond chance after allowing for that. The test ran its planned length and was not stopped early.
